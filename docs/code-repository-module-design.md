# AiAgent 代码库模块设计

日期：2026-07-10

## 1. 模块定位

代码库不是把源码文件上传到知识库后做相似度检索，而是一个可追溯的工程理解与诊断模块。

它要回答三类问题：

1. 工程理解：`这个代码库是做什么的？核心模块、启动入口、依赖关系是什么？`
2. 代码定位：`这个接口/页面/实体在哪里实现？调用了哪些服务？`
3. 故障分析：`前端页面报错可能在哪里？这段异常的根因、影响范围、排查步骤是什么？`

最终回答不能只有“可能是某处代码”。应提供可核验的证据：仓库、分支/提交、文件路径、符号、行号、调用链、配置项、日志片段和建议的下一步操作。

## 2. 参考 codex 目录得到的设计原则

`E:\项目\know-why\codex` 不是单一语言项目，而是包含 Rust 主体、TypeScript SDK、CLI、Bazel/Nix 构建、沙箱、协议和测试的 monorepo。其组织方式对本模块有四个直接启发：

- **工作区优先**：先识别 monorepo 根、子项目、语言和构建系统，不能把整个目录当成同一种代码。
- **边界优先**：例如 `codex-rs`、`codex-cli`、`sdk/typescript`、`scripts` 是不同责任域，问答和诊断要先落到责任域。
- **配置与运行态同等重要**：`AGENTS.md`、`package.json`、`Cargo.toml`、`BUILD.bazel`、CI、环境变量和启动脚本常常比普通源码更能解释“项目怎么运行”。
- **上下文有预算**：源码不能无限塞给模型。索引层保存结构化摘要和关系，问答阶段按问题逐步读取必要证据。

## 3. 产品信息架构

左侧导航建议新增一级入口：`代码库`，与“知识中心”平级。代码库首页沿用知识中心的列表式信息架构，但卡片展示工程状态而不是文档数量。

```text
代码库
├── 代码库列表
│   ├── 新建代码库
│   ├── 刷新 / 同步
│   └── 每个仓库的索引状态、分支、最近提交、诊断状态
└── 代码库详情
    ├── 概览
    ├── 文件与符号
    ├── 架构地图
    ├── 依赖与调用链
    ├── 运行与错误
    ├── 索引版本
    └── 设置
```

聊天输入框中的知识库选择器可扩展为“上下文来源”：`无`、`知识库`、`代码库`、`知识库 + 代码库`。当选择代码库时，Agent 可以调用代码检索与诊断工具；没有选择时，不能凭空引用本地代码。

## 4. 创建代码库

第一版应支持本地目录，Git 远程仓库作为第二阶段能力。

创建弹窗建议包含：

| 区域 | 配置 | 说明 |
| --- | --- | --- |
| 来源 | 本地目录 / Git 仓库 | 第一版默认本地目录；Git 仓库预留 URL、认证和分支。 |
| 基本信息 | 名称、显示名称、说明、标签 | 名称用于稳定标识；说明帮助 Agent 理解业务背景。 |
| 范围 | 根路径、包含目录、排除目录 | 根路径必须明确；默认排除 `node_modules`、`bin`、`obj`、`dist`、`build`、`.next`、`.git`。 |
| 同步 | 当前分支、同步策略 | 支持手动、启动时检测、定时扫描；第一版只做手动与启动检测。 |
| 语言提示 | 自动识别 / 手动补充 | 自动识别 C#、TypeScript、Python、Rust、Java 等；可手动标记主技术栈。 |

不要在创建时直接执行构建、安装依赖或运行脚本。创建只负责验证路径、扫描元数据并建立索引任务，执行命令必须单独授权。

## 5. 设置页设计

设置页应采用“少量高频配置 + 高级折叠区”的形式，避免把工程分析能力做成一堆晦涩开关。

### 5.1 常规

- 代码库显示名称、业务说明、标签。
- 项目根目录与仓库类型。
- 默认分支或本地基准提交。
- 是否作为聊天默认代码上下文。
- 只读开关：第一版固定只读，后续才允许 Agent 创建补丁。

### 5.2 扫描范围

- 包含路径：默认整个仓库，可添加子项目目录。
- 排除路径：支持 glob，内置常见构建产物和依赖目录。
- 最大单文件大小、最大索引文件数、二进制文件策略。
- 文件类型白名单/黑名单。
- 是否读取 `README`、`AGENTS.md`、`CONTRIBUTING.md`、CI 配置、容器配置、构建文件。

建议提供“扫描预览”：显示会纳入多少文件、排除多少文件、体积最多的目录，避免误索引 `node_modules` 或产物目录。

### 5.3 代码理解与索引

- 解析器策略：`自动`、`轻量文本`、`语法树增强`。
- 结构化解析开关：符号、导入/引用、继承/实现、路由、依赖清单、配置键。
- 分块策略：按函数/类/模块优先；无法解析时才按文本长度切块。
- 摘要生成：项目摘要、模块摘要、目录摘要、关键入口摘要。
- 嵌入模型与检索配置：复用知识库已有模型配置，但代码库单独保留 `top_k`、重排、最大上下文预算。
- 索引版本与增量策略：完整重建、按文件哈希增量、按 Git diff 增量。

### 5.4 构建与运行信息

这是代码库区别于普通知识库的重要设置。

- 检测到的包管理器和构建系统：例如 `dotnet`、`npm/pnpm`、`cargo`、`Bazel`、`Python`。
- 启动命令：前端、后端、测试、lint 各自独立配置；只做保存与校验，不自动执行。
- 工作目录、环境变量名称清单、端口、服务 URL。
- 配置文件映射：如 `appsettings.json`、`.env`、`next.config.*`、`launchSettings.json`。
- 机密字段策略：只记录变量名，默认不采集值；API Key、连接串、Token 必须脱敏。

### 5.5 诊断

- 日志来源：手工粘贴、上传日志文件、后端日志目录、浏览器错误导入。
- 错误上下文：时间窗口、环境、服务名、版本/提交号、浏览器 URL、操作步骤。
- 诊断深度：快速定位 / 标准分析 / 深度调用链分析。
- 工具权限：允许读取文件、允许搜索 Git 历史、允许执行只读诊断命令；执行命令默认关闭。
- 诊断数据保留期与脱敏规则。

### 5.6 同步与安全

- 文件变动检测状态与上次扫描时间。
- 是否允许访问 `.git` 历史；默认只读取提交元数据，不读取远程凭据。
- 忽略规则来源：内置规则、`.gitignore`、用户规则。
- 路径访问白名单：所有实际读取都必须位于代码库根目录内。
- 删除代码库时：仅删除索引与元数据，绝不删除原始仓库文件。

## 6. 详情页建议

### 概览

第一屏应直接回答“这是什么项目”。包括：

- 一句话项目说明：由 README、入口、依赖和模块摘要综合生成，可人工编辑覆盖。
- 技术栈卡片：语言、框架、包管理器、构建系统、数据库/消息队列等。
- 架构地图：前端、后端、共享库、脚本、基础设施等模块及其依赖方向。
- 关键入口：Web API 入口、前端路由入口、CLI 入口、后台任务入口。
- 风险提示：索引过期、构建配置缺失、未识别的运行命令、最近诊断错误。

### 文件与符号

- 左侧为目录树，支持按文件名、符号名、类型过滤。
- 右侧显示源码预览、符号大纲、导入/被引用位置。
- 函数、类、接口、路由、配置键都应是可点击实体。
- 代码问答返回的引用可直接跳转到文件和行号。

### 架构地图

- 先提供目录/模块树和可读的依赖列表，不急于做复杂可视化。
- 第二阶段再引入交互图：模块依赖、HTTP 路由到服务、前端页面到 API、数据库实体到服务。
- 图上的每个节点都可打开对应模块摘要和代码证据。

### 运行与错误

这是用户排查“前端页面异常可能在哪里”的主要工作台。

输入一条错误后，系统按以下顺序收集证据：

```text
错误信息 / 堆栈 / 浏览器 URL
-> 解析异常类型、文件、行号、接口地址、组件名
-> 精确定位源码与配置
-> 读取相邻调用链、相关路由和接口
-> 检索相似历史错误与最近 Git 变更
-> 由 LLM 生成：可能根因、证据、验证步骤、修复建议、影响范围
```

诊断结果必须区分：

- 已证实：有堆栈、代码或配置直接支持。
- 高概率：有调用链和上下文支持，但尚未复现。
- 待验证：需要用户补充日志、环境变量、网络请求或复现步骤。

不要把“猜测”写成根因。每一个结论都应附有证据引用和验证命令/操作。

## 7. 代码索引的数据模型

建议独立于 `AiKnowledgeBase`，避免把代码库的版本、Git 信息和符号关系硬塞进文档知识库表。

```text
ai_code_repository
  Id, Name, DisplayName, RootPath, SourceType, DefaultBranch,
  Description, TechStackJson, SettingsJson, Status,
  LastScannedAt, LastIndexedAt, CreatedAt, UpdatedAt

ai_code_snapshot
  Id, RepositoryId, GitCommit, GitBranch, FileCount,
  Status, DiagnosticsJson, CreatedAt

ai_code_file
  Id, RepositoryId, SnapshotId, RelativePath, Language,
  ContentHash, SizeBytes, IsGenerated, IsTest, MetadataJson

ai_code_symbol
  Id, RepositoryId, SnapshotId, FileId, QualifiedName,
  Kind, StartLine, EndLine, Signature, Summary, MetadataJson

ai_code_relation
  Id, RepositoryId, SnapshotId, FromSymbolId, ToSymbolId,
  RelationType, EvidenceJson

ai_code_chunk
  Id, RepositoryId, SnapshotId, FileId, SymbolId,
  StartLine, EndLine, Content, EmbeddingRef, MetadataJson

ai_code_diagnostic
  Id, RepositoryId, SnapshotId, SourceType, Severity,
  RawInput, NormalizedError, AnalysisJson, CreatedAt
```

关系类型第一版可覆盖：`imports`、`calls`、`implements`、`extends`、`route_to_handler`、`component_to_api`、`reads_config`、`uses_entity`。不要求一次性解析所有语言；无法确定时保留文本证据即可。

## 8. Agent 工具设计

代码库接入现有 `AgentContext -> ToolProtocol -> ToolDispatcher -> AgentLoop` 时，建议增加以下只读工具：

| 工具 | 用途 |
| --- | --- |
| `code_search` | 按自然语言、文件名、符号名、错误文本检索代码块。 |
| `read_code_file` | 读取限定行范围的源文件，并返回路径和行号。 |
| `find_symbol` | 查找类、方法、接口、路由、组件、配置键。 |
| `trace_call_path` | 查找调用者/被调用者，第一版只返回有证据的局部链路。 |
| `inspect_project_map` | 读取项目、模块、技术栈和入口摘要。 |
| `inspect_runtime_config` | 定位启动命令、端口、环境变量名和配置文件引用。 |
| `analyze_error` | 对错误文本、堆栈、网络请求和选定文件进行结构化诊断。 |
| `git_diff_search` | 检索指定提交或最近变更中可能相关的文件。 |

工具输出应是结构化 evidence，不应直接生成最终答案。最终回答由 LLM 根据 evidence 组织，并附路径/行号引用。

## 9. 前端异常分析示例

用户问题：`我的前端 /settings/models 页面报错，可能是哪里有问题？`

建议的 Agent 路径：

```text
1. analyze_error
   输入：浏览器错误、堆栈、URL、浏览器控制台日志。
2. find_symbol / read_code_file
   定位页面组件、依赖组件、API 调用和 i18n key。
3. trace_call_path
   查找页面 -> hook -> API client -> 后端路由的链路。
4. inspect_runtime_config
   核查前端 API Base URL、代理、CORS、环境变量和后端端口。
5. git_diff_search（可选）
   查看最近改动是否涉及相关文件。
6. FINISH
   输出：根因排序、每项证据、验证步骤、建议修复位置。
```

答案样式示例：

```text
结论：最高概率是 SettingsPageHeader 使用了未定义变量 t。

证据：
- front/components/.../SettingsPageHeader.tsx:xx 使用 t("...")。
- 该组件未调用 useI18n()，也未通过 props 接收 t。
- 浏览器堆栈命中同一组件和行号。

建议：
1. 在组件内调用 useI18n()，或由父组件传入翻译函数。
2. 刷新后访问 /settings/models 验证。

待验证：若修复后仍失败，检查对应 i18n key 是否存在。
```

## 10. 分阶段实施建议

### 阶段 1：可用的工程理解

- 本地目录注册、文件扫描、语言/构建系统识别。
- 文件级和符号级索引，生成项目/模块摘要。
- `code_search`、`read_code_file`、`find_symbol`。
- 代码库概览页、文件与符号页、设置页。

验收：能够回答“这个仓库做什么”“启动入口在哪里”“某个类/页面在哪”。

### 阶段 2：诊断闭环

- 错误输入、堆栈解析、日志导入。
- 前端路由/API/后端控制器/配置关联。
- `analyze_error`、局部 `trace_call_path`、诊断报告与证据引用。

验收：能够对真实异常给出根因排序、代码定位和验证步骤。

### 阶段 3：Git 与增量索引

- 读取 Git 状态、提交、Diff。
- 按文件哈希/提交增量更新。
- “这个异常是否可能由最近改动引入”的分析。

### 阶段 4：受控执行与修复建议

- 将构建、测试、lint 作为显式授权的诊断工具。
- 统一沙箱、超时、资源限制、命令白名单和日志脱敏。
- Agent 可生成补丁建议；实际写文件仍需用户确认。

## 11. 第一版不做的事情

- 不自动安装依赖、启动服务、执行构建或修改源代码。
- 不在未经确认时读取仓库根目录外的文件。
- 不采集 API Key、连接串、Token 等密钥值。
- 不承诺完整静态分析或全语言调用图。
- 不把生成目录、依赖目录和大体积二进制文件纳入语义索引。

## 12. 推荐的设置页首版布局

```text
代码库设置
├── 常规
│   名称 / 说明 / 根目录 / 默认上下文
├── 扫描范围
│   包含目录 / 排除规则 / 扫描预览
├── 索引与理解
│   自动识别技术栈 / 符号解析 / 分块 / 嵌入模型 / 增量策略
├── 运行信息
│   前端命令 / 后端命令 / 测试命令 / 端口 / 环境变量名称
├── 诊断
│   日志来源 / 诊断深度 / Git 历史 / 只读工具权限
└── 危险操作
    清理索引 / 删除代码库元数据
```

页面顶部固定展示：当前快照、分支/提交、索引状态、最近扫描时间和“重新扫描”按钮。这样用户在提问或诊断前始终能判断代码证据是否新鲜。
