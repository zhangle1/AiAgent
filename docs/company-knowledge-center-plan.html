AiAgent · Knowledge Center Blueprint · 2026-09-14

让公司知识从“文件堆”变成可治理、可检索、可调用的上下文基础设施

基于现有 .NET 9、Next.js、Knowledge/RAG 与 CodeRepository 能力，建设统一的公司、项目、人员与技能知识中心，并以 guokun:// 逻辑地址向 Agent 和外部 API 提供一致的服务。

01 · 核心判断

不另起一套孤立的 LLM Wiki。应在现有 Knowledge/RAG 之上增加 Knowledge Center 领域层：资源目录管“是什么、属于谁、谁能看”，处理流水线管“如何变成知识”，检索服务管“如何找到并引用”。
数据源→版本快照→解析→AI 提炼→审核发布→Search / Read / Answer

首期优先级：目录、权限、上传、提炼、检索、引用、API Key。知识图谱、自学习 Agent、数据库 CDC 放到数据证明必要之后。

02 · 现状与差距

已有底座知识处理链路知识库、文档、Chunk、索引版本、后台 Job、LlamaIndex 构建均可复用。
已有入口Web 与 Agent已有知识管理 UI、搜索 API、引用 DTO 和 Agent RAG/按页读取工具。
已有权限事实项目成员关系AiUserCodeProject 可作为项目知识授权的首个来源。

真正缺少的是公司级治理层

  • 知识库没有组织、项目、团队、人员等明确归属。
  • 没有稳定 URI、目录浏览和跨库统一排序。
  • 没有摘要、技能卡、代码地图等独立 AI Artifact 及审核发布。
  • 没有 API Client、Scope、配额、轮换、限流和审计。
  • 现有知识 API 应统一接入身份上下文，不能只靠 kbName 判断权限。

03 · GitHub 同类项目的可取之处

项目借鉴不照搬
OpenVikingURI 资源定位、目录浏览、abstract/overview/原文分层读取不替换现有 SQL、文件存储和 LlamaIndex；URI 不映射为公开物理路径
RAGFlow按文档类型解析、Chunk 可视化干预、发布前检索测试不引入整套平台承担已有能力
Dify本人/全团队/部分成员的数据集权限，外部知识源与服务 API权限仍以 AiAgent 用户与项目模型为事实来源
AnythingLLMWorkspace 用户授权、OpenAPI 与机器访问不让 Web 与 API Key 绕过同一个策略引擎

05 · guokun:// 命名空间

guokun://{tenant}/{scope}/{owner}/{collection}/{logical_path}

scope      = org | project | team | user
collection = wiki | code | document | skill | runbook | decision | dataset

guokun://acme/project/aiagent/code/backed/Services/Knowledge/README.md
guokun://acme/user/u-1024/skill/dotnet-api-review.md
  • URI 是稳定逻辑定位符，不是数据库主键或物理文件路径。
  • 重命名用 alias/redirect 保留历史引用。
  • URI 只表示位置；每次 list/read/search 仍需服务端鉴权。
  • 搜索引用带 URI、资源版本、页码/行号；代码引用绑定 commit SHA。

06 · 核心领域模型

对象职责关键语义
KnowledgeSpace知识边界tenant、org/project/team/user、owner、visibility
KnowledgeCollection业务集合wiki、code、skill、document、pipeline
KnowledgeResource稳定逻辑资源canonical_uri、classification、current_version
ResourceVersion不可变快照content_hash、source_revision、parser_version
SemanticNode分层摘要L0 abstract、L1 overview、L2 原文节点
KnowledgeArtifactAI 派生产物类型、模型、prompt 版本、置信度、审核状态、引用
AccessControlEntry资源授权subject、URI prefix、action、allow/deny
Publication原子发布release、index version、approver、rollback
人员技能是敏感派生信息。默认仅本人和获授权管理者可见；每条技能结论必须有证据、有效期，支持本人纠错和撤回。AI 产物不能静默覆盖原文。

07 · 处理与检索流水线

Discover→Snapshot→Validate→Parse/OCR→Segment→Artifacts→Index→Review→Publish
  • source_version + pipeline_config_hash 保证幂等。
  • 新版本全部校验成功才原子激活，失败不影响当前版本。
  • 删除/撤权先从检索逻辑隔离，再异步清理物理向量。
  • 检索先解析可见 URI 范围，再混合召回，之后再次做策略过滤。
  • Search 返回证据；Answer 在证据上生成内容，两者分离。

08 · 对外 API 产品化

能力建议接口
浏览空间GET /api/v1/knowledge-center/spaces
目录列表GET /resources?parent_uri=...
读取资源GET /resources/{id}/content
证据检索POST /search
引用回答POST /answers
同步来源POST /sources/{id}/sync
任务进度GET /runs/{id}

安全底线

  • Key 只展示一次，服务端只存强哈希与前缀；支持轮换、过期、吊销。
  • Scope 细分 list/read/search/answer/write/admin，并限制 URI 前缀。
  • IP allowlist、限流、日配额、最大 top_k、cursor 分页和 request_id。
  • 审计记录主体、范围、命中资源、耗时与结果，不记录完整敏感原文。
  • 永不返回 StoragePath、向量路径、绝对路径或内部异常堆栈。

10 · 八周 MVP 与验收

范围org/project/user 三种空间；document/wiki/code/skill 四类集合。
接入文件上传 + 一个 Git 仓按 commit 增量同步。
产物abstract、overview、outline，全部带血缘与审核状态。
权限viewer/editor/owner，继承现有项目成员授权。
服务list/read/search，API Key read/search Scope、限流与审计。
兼容旧 Knowledge API 与 Chat 通过 Adapter 平滑迁移。

核心指标

安全越权检索与精读 0 泄漏；撤权即时生效
检索真实评测集 Recall@5 ≥ 0.80；引用可定位率 ≥ 95%
稳定失败版本不影响线上；任务可幂等重试和单资源恢复
解释100% 结果带 URI、版本和页码/行号
默认决策建议：单租户部署但预留 TenantId；个人技能默认私有；外部 API 首期只开放 list/read/search；GraphRAG 延后到评测证明需要时。
