# 聊天消息排队与原生追加

## 使用

普通聊天正在执行时，仍可输入并发送后续消息。输入框显示「继续投递」：

| 方式 | 行为 |
| --- | --- |
| 排队继续，默认 | 服务端先保存消息，前一轮成功保存回答和完成事件后，再启动下一条 |
| 追加当前任务 | Codex app-server 有可用的活动轮次，且模型、权限和引用上下文一致时，发送原生追加；不支持时明确拒绝 |
| 自动选择 | 可原生追加时追加，其他普通场景排队；不通过中断重启伪装成原生追加 |

收到「已投递」只代表投递确认，当前任务仍可能运行、失败或尚未采纳该要求。待处理消息在输入框上方独立显示，可取消未执行项。没有待处理消息时隐藏队列。停止按钮只停止当前执行，后续排队项保留并挂起。失败、断线或服务重启后也保留待执行输入，由「恢复执行」明确启动；不会自动重发结果未知的任务。

Codex app-server 的排队轮次复用服务器保存的原生 thread，延续已有上下文；项目、引用范围、技能选择、实际工作区、模型、Profile 和权限模式组成绑定指纹，变化后使用独立 thread。浏览器不能提供原生 thread／turn ID。旧普通请求仍沿用临时 thread；目标模式保持独立的原生目标暂停／继续协议，活动目标先暂停再投递普通消息。

## 实现与生命周期

参考用户提供的 [t3code 源码解析](E:/项目/know-why/代码理解/t3code-消息排队与追加指令源码解析.md) 及本地源码中的投递意图、排队、原生追加与挂起分离思想，沿用本项目的 C# HTTP／WebSocket、命令去重和在线执行生命周期。

- `ChatDeliveryService` 负责持久化待执行请求、同会话串行准入、指纹去重、排队顺序、挂起／取消／恢复和归属检查。
- `ChatCommandStore` 继续在真正执行之前登记命令并保存展示事件，重复请求只回放。排队时尚未调用模型，也没有创建假的助手回答。
- HTTP SSE 和 WebSocket 共用准入逻辑。执行取得位置后，重新验证网页登录身份、项目、附件、引用与模型配置，再进入原有编排和历史保存流程。
- `CodexTurnControl` 仅绑定服务器当前活动轮次。`CodexChatService.Steering.cs` 通过唯一 stdout 读取器分发各 RPC 回应，写入串行化，避免追加请求与原请求抢读。
- 追加先保存用户输入，再发送 `turn/steer`，包含 `threadId`、`expectedTurnId` 和输入；RPC 接受不广播整轮完成。确认超时、拒绝或连接不确定时，记录为待确认，不自动重投或悄悄转为排队。
- 带附件的原生追加共用普通发送的所有权与图片策略校验。文档提取为不可信证据，图片使用服务器持久化后的 `localImage`，只发送到已绑定的活动轮次。附件失效或无权限时，在写入用户记录和发送 RPC 前拒绝；这类失败不挂起无关排队项。
- 每个等待连接有排队心跳；断开后持久化记录继续保留。服务启动不会自动接管遗留活动运行，原活动行变为 `uncertain`，未开始的消息挂起。

`ai_chat_delivery` 使用用户与命令编号的 SHA-256 主键，保存本人会话、完整请求快照、指纹、单调队列位置、状态、独立 Held 标记和进程标识。原生 thread ID 与配置绑定仅在服务端保存；列表响应不返回它们或完整内部请求。

待执行内容属于用户聊天数据，与聊天数据库使用相同的访问边界，不作为脱敏日志。请求快照只序列化客户端字段，不保存网页登录 Token、解析后的服务器路径、运行委托或模型密钥。每次准入和恢复重新检查当前身份与权限。

状态包括 `queued`、`running`、`steering`、`steered`、`completed`、`failed`、`cancelled`、`uncertain`；`Held` 与状态分离。普通失败阻止后续自动启动，手动恢复仅限从未开始的 `queued` 行。取消待执行消息不会中断当前任务，也不会把取消记录重新当作新任务执行。

## 协议

现有聊天流请求增加可选字段：

```json
{
  "session_id": "本人会话编号",
  "command_id": "每次新操作的稳定编号",
  "message": "后续要求",
  "delivery_intent": "queue"
}
```

`delivery_intent` 为 `queue`／`steer`／`auto`。相同编号不能更换文本、配置、附件、会话或投递意图。显式恢复以原编号发送 `resume_queued=true`，服务端加载原始快照，忽略替换正文。`recover_only=true` 只查询旧结果或待执行状态，不能启动排队任务。

新增展示事件：

| 事件 | 含义 |
| --- | --- |
| `delivery_queued` | 请求已保存，正在等待；也用作等待心跳 |
| `delivery_started` | 已取得执行位置，用户消息持久化后进入执行 |
| `delivery_held` | 待执行项挂起、已取消或结果待确认，连接可以结束 |
| `delivery_steered` | 原生追加已接受，投递连接结束，当前任务继续 |

`completed` 继续只用于原有整轮回答保存成功后的确认。前端不会把排队、挂起或追加确认合成为新的助手完成事件，也不会据此触发原型生成等完成后动作。

- `GET /api/v1/chat/sessions/{sessionId}/deliveries`：返回本人可见的排队／活动／待确认项，包含命令编号、文本预览、位置、状态和 `queue_held`。新建但尚未建立的会话、他人或已删除会话返回空列表。
- 原有 `POST /api/v1/chat/commands/{commandId}/cancel?session_id=...`：同时支持取消队列项或停止活动投递，保留原普通命令取消兼容行为。

## 部署与边界

新增表由原有启动 CodeFirst 阶段创建，初始化顺序保持。禁用 CodeFirst 的部署须先创建该表、索引及可空原生绑定字段。前后端应同步更新，旧请求兼容原有入口。

本版继续面向单 API 实例和在线连接执行，不是脱离连接的后台 Agent。浏览器关闭后不会丢失待执行快照，但需要明确恢复；多实例接管需要另加分布式租约。每会话最多 100 条待执行消息，请求快照最多 200 万字符，正文最多 20 万字符。附件排队期间若失效，执行会失败并挂起后续消息，不悄悄删掉附件再发送。

原生追加仅支持可用的 Codex app-server 普通轮次；exec Profile、其他引擎、准备阶段、改变模型／权限／引用上下文的请求可排队，显式原生追加会拒绝。本版不实现 interrupt + restart。用量不足按既有 Provider 错误处理并挂起后续项，不保证达到额度后自动恢复，也不改变目标预算。

## 验证

隔离 SQLite 测试覆盖顺序、重复、停止、取消、断线、进程重启、权限变化、原生追加确认／未知结果、绑定持久化与恢复。SSE 和 WebSocket 集成验证相同队列规则、前一轮保存后再启动、重复排队不重复历史或模型调用。

Node 合成 app-server 通过实际 C# 进程 I/O 验证 `turn/steer` 的 expectedTurnId、并发回应、拒绝后继续、只有一个 stdout 读取器，以及排队轮次 `thread/start → thread/resume`。没有调用真实模型。

前端单元测试验证队列不会虚报完成、目标隔离、状态切换与重试边界；真实浏览器使用合成 HTTP／WebSocket 验证连续投递、追加确认、停止只取消当前命令、刷新后的手动恢复及 390px 布局。交付按实际暂存快照重新检查构建，排除此前未提交的其他功能。
