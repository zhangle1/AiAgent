# 知识库先完整入 Git，再由 Codex 管理的实施建议

日期：2026-11-05  
状态：方案讨论，未实施导出、上传、拉取、合并或推送。本文根据当前工程代码复核，调整上一版方案的实施优先级。

## 1. 重新理解目标

你的核心诉求是：先把已有知识完整变成可以浏览、搜索、修改和版本管理的文件仓库，让 AiAgent 聊天中的 Codex 面对真实文件工作；以后用实际使用和调试反馈，逐步改善知识库本身。

**建议采用“知识文件仓库优先”的路线。第一阶段交付完整可读的知识仓库和聊天访问能力，后续再建设持续同步、知识检索和自动整理能力。**

这里“完整”包含原始文件以及已存在、允许导出的解析正文和知识产物。无需先把所有文件重新提炼一遍，也无需等新的知识挂载和聊天沉淀界面完成。

与上一版方案相比，调整如下：

| 内容 | 本次建议 |
| --- | --- |
| 首个目标 | 已有知识完整导出到独立 Git 仓库，并接入 AiAgent 项目 |
| AI 获取信息 | 先通过真实目录、导航文件、关键词搜索和按需读文件 |
| 聊天维护 | 复用现有 Codex 文件操作能力，整理文件并形成可审阅 diff |
| Git 管理 | Codex 协助判断和准备，沿用项目交付权限完成提交与推送 |
| 知识库能力 | 保留现有服务，之后接入 Git 文件来源并逐步优化 |

## 2. 当前代码支持到哪一步

以下区分现有代码事实与待实现建议。

| 已核实代码 | 对本方案的意义 |
| --- | --- |
| `backed/Services/Chat/Codex/CodexChatService.cs` 的 `ResolveWorkspacePath` 使用所选 `AiCodeProject.RootPath`；进程和会话使用这个工作目录 | 知识文件进入当前服务端可访问、已授权的项目目录后，可利用现有 Codex 聊天入口开展文件工作 |
| `backed/Entities/CodeRepository/AiCodeRepository.cs` 已有 `ProjectId`、`RootPath`、`GitAccountId` | 可以将文档专用 Git 仓库作为普通仓库登记，账号仍按请求用户解析 |
| `backed/Services/Knowledge/KnowledgePathService.cs` 分别管理知识库 raw 与索引版本路径 | 原文件与运行时索引应分开处理，不能直接把数据根目录全部上传 |
| `backed/Services/Knowledge/KnowledgeResourceService.cs` 将数据库记录、解析存储与个人产物投影成资源树 | 页面上的完整知识树不等于一个可以直接复制的物理文件夹，需要导出器还原逻辑目录 |
| `backed/Services/Knowledge/KnowledgeWorkspaceService.cs` 从产物记录中的 `Content`、`EvidenceJson` 展开知识页 | 只复制 raw 会遗漏已有知识页及其证据，需要同时导出数据库中保存的有效内容 |
| `backed/Services/Git/CodeRepositoryGitService.cs`、`GitWorkspaceService.cs` 已有拉取及工作区 Git 操作入口 | 可复用现有 Git 基础，但仍要核对账号、并发、变更范围与交付检查 |

**“远端已经上传”与“当前聊天能够访问”是两个验收点。** Git 远端保存内容；AiAgent 的 Codex 实际读取其运行机器上的工作副本。必须克隆或导出到对应服务端，并正确登记项目路径、验证访问权限。仅粘贴远端地址或浏览器本地路径，不能证明文件已可读。

另外，当前代码使用项目根目录启动 Codex。不能假设选中了某个仓库，就已经自动切换进该仓库；聊天应明确知识仓库相对路径。

## 3. 首次上传：导出完整内容，而不是上传运行目录

建议创建独立的私有知识仓库，例如 `team-knowledge`。AiAgent 应用源码仓库保持现状，知识原文进入专用仓库。当前项目不提交本地知识原文的约定仍然适用。

“完整上传”的范围为用户明确选择且有权发布的知识集合。团队共享知识与个人知识按权限分仓；不能将所有人员空间合并上传后，期待子目录继续提供隔离。Git 仓库读取权限通常意味着能读取该仓库历史中的内容。

建议结构如下，名称是设计示例，不要求迁移现有生产目录：

```text
team-knowledge/
  README.md                    # 适用范围、目录说明、更新方式
  AGENTS.md                    # 给文件维护 Agent 的约定，不保存凭据
  catalog.md                   # 全库导航：主题、文件位置、简介
  sources/                     # 原始 Markdown、Office、PDF、图片等
  readable/                    # 已有解析正文、章节与必要的可读副本
  wiki/                        # 已有可导出的知识页
  summaries/                   # 已有文件或目录摘要
  manifests/
    export.json                # 导出版本、范围、文件数量与完整性信息
    documents.json             # 稳定来源标识、相对路径、内容哈希及关联
```

导出遵循这些规则：

1. 保留原文件字节、逻辑层级和原名称；遇到重名或非法路径，使用稳定标识消歧，并在清单保留映射。
2. 导出已经存在的解析正文、知识页和摘要，记录原文关联及生成时的来源哈希。旧摘要可以保留，但须标为过期，不能伪装成当前版本结论。
3. 尚未解析的文件照样导出原件，清单标记“暂无可读正文”。扫描 PDF、图片和二进制 Office 的可用性单独核验，不能声称完整上传就等于全部内容已经可检索。
4. 在受控临时目录构建导出结果，核对范围、数量、字节数和哈希后整体发布。导出失败不留下看似完整的知识仓库。
5. 不复制数据库文件、账号配置、Token、向量索引、临时文件和服务运行状态。需要迁移的元数据转换成不含凭据及服务器绝对路径的清单。
6. 超大原件先列清单，再根据实际 Git 托管限制决定普通 Git、LFS 或受控附件存储；若采用外部附件，明确它不属于“仅克隆即可完整获取”的交付状态。

导出器应复用知识资源可见性、现有解析存储与知识页展开逻辑，不能扫描整个数据目录来猜测内容和最新版本。本轮只设计流程，不读取或搬运真实用户数据。

## 4. 让聊天直接站在文件事实面前

最快的验证方式是建立一个“知识维护”项目，将知识仓库放在它的工作目录中，并登记为该项目仓库。使用现有聊天选择这个项目，即可围绕实际文件验证读取、整理和问答。

建议聊天时提供简短上下文：

```text
知识仓库：./team-knowledge
入口：README.md、catalog.md
先查看工作区状态，再搜索相关主题并按需读取正文。
回答注明实际读取的相对路径及章节或行号。
修改前检查来源关联；生成正文与原文存在差异时明确说明。
```

这段文字帮助定位文件，实际权限仍由项目授权与运行环境控制。

如果需要同时讨论业务代码和知识，可以在同一个已授权项目工作区登记两个并列仓库：

```text
project-workspace/
  application/                 # 业务代码仓库
  team-knowledge/              # 知识仓库
```

两个目录各自有 Git 历史，执行 Git 操作时明确工作目录。不要把知识仓库随意嵌入应用源码仓库造成嵌套跟踪，也不必第一阶段引入 submodule。

若现有项目布局不便调整，先完成独立知识项目；跨项目附加知识目录作为后续功能开发，不能用放宽全盘访问替代。

实际对话可以是：“先查知识仓库里的部署规范，再对照 application 当前配置分析问题。”Codex 根据需求检索和读文件；不把全库一次性放进提示词，也不把“文件存在”描述成“已读完全部资料”。

## 5. Codex 如何协助管理 Git

可以让 Codex 处理日常 Git 分析和变更准备。第一阶段无需重新开发完整 Git 聊天面板，但要承接现有交付规则，不能让命令行能力绕过权限与审批。

| 场景 | 建议处理方式 |
| --- | --- |
| 查看文件、状态、历史与差异 | 在授权工作区直接读取，回答对应文件和版本 |
| 整理知识、补文档、调整导航 | 在本轮独立工作区或分支形成 diff，记录修改范围 |
| 获取远端更新 | 校验远端和账号后 fetch，再比较本地与远端 |
| 拉取 | 工作区干净且可快进时采用快进更新；有未提交修改或分叉时先保留现场并形成处理方案 |
| 合并冲突 | 在隔离分支准备合并结果，说明保留与修改的内容，验证引用及文件完整性 |
| 提交、推送、向主分支交付 | 形成变更集并校验，具备提交权限的人工审批人确认后执行；交付前重新核对指纹和基线 |

知识整理引起的删除、重命名、链接变动也应进入明确 diff。不要使用“丢弃本地修改后拉取”作为默认同步方式，也不要把不相关文件一起暂存发布。

现有 Git 服务解析出的凭据，不能假设 Codex 的终端会自动继承。优先通过既有 Git 服务完成需要认证和交付的步骤；若增加聊天工具入口，应调用受控服务，不向提示词、仓库文件或日志输出凭据。

多人聊天和后台 Git 操作需要共享仓库锁或使用独立工作副本。当前服务的锁不能自动约束 Codex 自己启动的 Git 命令，这一点在正式开放聊天 Git 维护前必须补齐。

## 6. 迁移后由谁负责写入

这是比“能不能推上去”更需要先决定的问题。长期同时允许旧知识库上传和 Codex 改 Git，而不定义同步方向，会产生两个版本。

建议分为两个明确阶段：

**验证期：知识库保留原样，Git 是首次完整导出的副本。** Codex 在知识仓库中读取和整理；界面或文档明确这些修改暂未回写旧知识库。再次导出先比较首次导出基线、当前 Git 文件与新导出内容，不得覆盖 Codex 已有修改。

**正式迁移后：Git 管理选定范围的原文版本，知识库读取已发布 Git 版本。** 新增和修改原文进入 Git 变更流程；知识库继续提供浏览、解析、摘要和检索。旧上传入口可以逐步改成生成仓库待发布变更，避免同一原文存在两条独立写入链路。

知识库个人产物仍归本人。Codex 整理的 Wiki 属于派生内容，不能无记录地覆盖原始证据；导出的 readable 与摘要也不能反向覆盖原件。

后续同步建议按固定 commit 的内容哈希判断新增、修改和删除，只失效受影响的解析与摘要。同步文件不自动调用模型；重建知识能力作为独立、明确的动作。

## 7. 推荐实施顺序与验收

### 第一阶段：完整导出与聊天可读

开发一次性可重复执行的导出工具，生成原件、已有可读内容、导航及映射清单；接入独立知识仓库和 AiAgent 知识维护项目。首次远端发布前展示完整文件清单和权限范围。

验收：选定范围内每个文件均有导出或明确失败记录；原件哈希一致；已存在的知识页有对应文件；新工作副本可从远端恢复；聊天能定位并引用抽样文件。没有重新提炼也能完成这阶段。

### 第二阶段：聊天整理与 Git 协作

打通受控 Git 操作与变更集，验证拉取、差异分析、文档修改、冲突处理和经审批的交付。先使用合成资料与临时本地 Git 远端，覆盖脏工作区、远端前进、并发修改、认证失败和审批后内容变化。

验收：修改范围可审阅，未知改动不丢失，远端未成功更新时不显示“已推送”，失败和取消保留可恢复现场。

### 第三阶段：知识库消费 Git

增加仓库、分支、相对目录和已同步 commit 的绑定；将 Git 原文映射到现有知识资源。逐步接入已有 L2、L0/L1、Wiki 与检索服务。

验收：Git 更新后能明确看到同步与解析状态；过期摘要不会显示成当前结论；不同用户的仓库及个人知识仍隔离。

### 第四阶段：按真实使用改善知识能力

根据聊天中找不到资料、重复文档、旧结论和导航不足等问题，逐步引入目录摘要、来源追踪、链接检查及整理建议。优化始终有对应 Git diff 和原文证据可查。

## 8. 建议的首轮交付边界

首轮只做三件事：**将选定知识完整导出为文件、放进独立 Git 仓库、让现有 AiAgent Codex 聊天能够读取并验证。** Git 维护先复用现有项目与交付流程，再补聊天中的受控衔接。

本方案保留上一版的长期关联方向，但把完整文件仓库作为起点。这样每一步调试都有实际目录、文件差异和版本可对照，也能让 Codex 从第一阶段就参与知识整理。
