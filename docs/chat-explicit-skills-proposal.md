# 聊天窗 `/` 主动技能：调研与实施建议

日期：2026-11-06。本文保留最初调研方案；已实现的 23 项技能、实际边界和验证方式见 [聊天主动技能](chat-explicit-skills.md)。下文的“建议”和“尚未实现”描述调研时状态。

## 1. 建议

可以做。把常用提示词整理成用户能理解的“技能”，用户在聊天输入框输入 `/`，选择技能、补充内容后发送。例如选择“需求追问”，再输入“我想调整知识库目录”。

本批技能统一为 **仅用户主动调用**：没有明确选择或调用，就不把技能正文、触发描述或候选清单放入模型上下文。不能让模型因为“正在讨论需求”就自动开始 Grill Me。

第一版建议支持一个技能、文本提示词、中文名称和预览。不直接安装整个 GitHub 技能库，不执行技能附带脚本。普通聊天和知识编译技能分开管理。

## 3. 输入框如何交互

```text
输入 /                         输入 /grill 或 /追问
┌───────────────────────────────┐
│ 技能                          │
│ 需求追问       /grill-me       │
│ 整理需求规格   /to-spec        │
│ 拆分任务       /to-tickets     │
│ 协作文档       /doc-coauthoring │
│ 周报与沟通稿   /internal-comms │
│ ───────────────────────────── │
│ 项目 / 文档（保留现有入口）    │
└───────────────────────────────┘

选中后：
[需求追问 ×]  我想调整知识库目录……
说明：发送后开始追问，结束前不会直接实施。
```

- 菜单显示中文名称、作用、示例，支持中文/英文搜索、上下键、Enter/Tab 选择、Esc 关闭。选中只添加标签，不自动发送。
- 可预览完整提示词；标签可删除。选中后的 Enter 行为恢复正常发送，避免选择与发送发生在同一次按键。
- 兼容中文输入法组合态；菜单用 Portal 避免被输入框裁剪，移动端可点击选择。
- 第一版一次选一个技能，避免“追问”与“直接生成”互相冲突。其他技能不能由当前技能隐式串联。
- 普通模式发送后清空待选技能；切换项目、会话清空草稿技能并阻止旧列表响应覆盖当前状态。
- 同一轮可保留已有附件和项目引用。与可视化模式冲突时给出可理解的选择，不能让两份提示词互相覆盖。

## 4. 什么才算用户主动调用

| 输入情况 | 是否启用 |
| --- | --- |
| 从 `/` 菜单选中并发送 | 是 |
| 消息开头输入完整 `/grill-me 我想……` | 是，规范化成相同的结构化选择 |
| 直接写“请用 grill me 帮我梳理……” | 建议显示“使用需求追问”候选标签，用户点击后启用；首版不靠模型判断自然语言意图 |
| “grill me 是什么意思？”、引用别人说的话 | 否 |
| 代码块、文档、检索结果中出现命令 | 否 |
| 只谈需求、写文档、报错，未选择技能 | 否 |
| 历史曾用过，但新一轮未选择且不在显式追问流程中 | 否 |

不使用关键词包含判断，例如正文出现 grill 就加入。完整命令只在顶层用户消息的起始位置识别，命令必须有空白或消息结束边界；保留现有 `/spec` 文档命令，不改为技能命令。

## 5. 多轮追问的生命周期

单次生成类技能仅作用于本轮。Grill Me、协作文档这类多轮技能，需要用户看得见的流程状态，否则用户每回答一句都得重选。

建议状态为：`未启用 → 用户显式开始 → 等待回答/继续 → 已结束`。

- 由首次显式调用创建流程，后续用户回答沿用已授权的同一流程，输入框持续显示“需求追问进行中 [结束]”。这不是按话题自动启用。
- 后端按用户和会话保存流程 ID、技能版本与状态，不用浏览器全局变量跨会话延续。
- 用户点击结束、输入明确退出命令或切换技能时结束；完成后继续普通聊天。退出时明确区分“终止正在流式生成”和“结束技能流程”。
- 新会话不继承，切换项目结束流程；切回旧会话展示状态，恢复追问需显式点击继续。刷新也需用户确认继续。
- 结束后不再新增技能正文；历史消息和原生代理 resume 仍可能保留过去指令。新轮应有明确的流程结束边界，并在运行适配层验证旧指令不持续生效。不能声称清除数据库状态就能抹除模型历史；无法可靠隔离的通道须新建运行上下文或暂不开放多轮技能。
- 选中技能不等于授权修改文件、创建工单或发布内容；例如追问完成只整理结论，不顺带开始开发。

## 7. 目录、接口与快照设计

建议内置技能以受控资源随服务端发布；用户自定义技能后续另做，只允许本人读取。技能管理不依赖 GitHub 实时请求，GitHub 仅为管理员导入来源。

目录记录建议包含：`id`、`slug`、中文名称、描述、别名、版本、正文、正文 SHA-256、上游仓库/commit/path、许可证、改编说明、作用域和启用状态。强制 `invocation_policy = explicit_only`。

建议接口：

- `GET /api/v1/chat/skills`：按当前身份返回可用菜单信息，不将全部正文送模型。
- `GET /api/v1/chat/skills/{id}?version=...`：供用户预览已发布版本。
- 聊天请求新增可选 `skill_invocation: { skill_id, version, flow_id? }`；未选择时为空。
- 服务端验证当前用户、会话/项目访问权、技能可见性和版本后解析正文；不信任前端传来的正文、任意文件路径或 URL。
- 首次发送保存原始用户文字与不可变快照，包含最终适配正文、版本、哈希、触发方式及流程 ID。重试通过原消息/调用 ID 找服务端快照并复核归属；不能只保存哈希，也不能根据旧 ID 读取最新正文。
- 已禁用技能禁止新调用；重试保留原内容，若当前策略禁止执行则明确拒绝，不静默替换。

运行层只加入本轮已选技能，以用户主动选择的任务约定传给模型，不能提升为可覆盖系统规则的权限。所有通道共用同一解析结果；不支持该能力的运行通道明确提示不可用。

技能正文不注册到原生代理的自动发现目录，不把本批技能 description 塞进全局系统提示。仅靠 `disable-model-invocation` 文本声明不足以满足“未提及不加入”。

## 8. 一份中文提示词可以长什么样

下面是供产品评审的原创简版草案，并非直接复制上游：

```text
技能：需求追问
目的：帮助用户把当前想法梳理成明确需求。

围绕用户刚提出的主题开展访谈。先问影响最大的一个未决问题，
给出 2～4 个具体选项并说明建议；等待用户回答后再继续。
已能从授权上下文确认的事实不重复问，把事实与建议分开。
依次澄清目标用户、当前痛点、期望行为、范围、边界和验收方式。
允许用户跳过问题、纠正方向或随时结束。
收敛后整理已定事项、未决问题与验收清单。
本流程只访谈与整理；不因访谈结束而自行启动开发或发布。
```

中文名称、菜单示例和引导语对易用性比技能数量更重要。用户无需理解 SKILL.md，只需知道“选这个，AI 会怎么帮我”。

## 9. 实施顺序与验收

1. 整理首批五个提示词，审阅依赖及许可证，固定来源版本与适配正文；确定单轮/多轮属性。
2. 做技能目录、预览、显式选择、服务端校验、历史快照和单轮调用，先打通普通聊天链路。
3. 做多轮流程状态、结束/恢复、原生代理 resume 隔离，再开放需求追问等持续流程。
4. 完成针对行为的测试及必要前后端检查，再更新 README/AGENTS 和交付变更集。

关键验收：

- 未调用技能时，捕获到的模型请求不含本批技能正文、清单和自动触发描述，普通聊天路径保持原行为。
- `/` 菜单和 `/spec`、项目引用、原型入口互不抢占；中文输入法、键盘选择和移动端可用。
- 解释技能名字、引用命令、代码块内命令不启用；用户删除标签后不启用。
- HTTP/WebSocket、自动重试、手动重试及历史恢复使用相同快照，不重复包装；技能更新后重试仍使用原版本。
- 双用户不能访问对方自定义技能、流程或快照；篡改版本/流程 ID/来源路径被拒绝。
- 多轮追问可以回答、结束与显式恢复；结束后普通消息不延续旧技能行为，原生代理 resume 单独验证。
- 当前技能不能自动调用本批其他技能，也不能依靠上游安装器、脚本、钩子绕过显式选择。

本次交付仅为调研方案；未安装技能、修改聊天功能或执行提交推送。
