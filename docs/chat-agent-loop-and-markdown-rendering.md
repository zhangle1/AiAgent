# AiAgent Chat Agent Loop and Markdown Rendering

Date: 2026-07-08

## Goal

The home page chat should behave more like DeepTutor:

- The assistant answer is generated by the configured LLM, not by directly showing nearest chunks.
- Knowledge-base access is exposed as tools.
- The model chooses when to call tools through a label protocol.
- Final answers are rendered as Markdown, so headings, tables, quotes, lists, and code blocks look like a real article.
- Streaming metadata carries loop rounds, call counts, and estimated token counts for the UI.

## Frontend Flow

Main files:

- `front/components/chat/KnowledgeChatHome.tsx`
- `front/components/chat/MarkdownMessage.tsx`
- `front/lib/chat-api.ts`

Flow:

1. The user sends a message from `KnowledgeChatHome`.
2. `streamCompleteChat` opens `ws://.../api/v1/chat/ws` and sends the chat request as JSON.
3. If WebSocket cannot connect, the client falls back to `POST /api/v1/chat/complete/stream`.
4. Stream events update one assistant message in place.
5. `content` events append visible final-answer text.
6. `thinking` events are kept in a collapsible details block.
7. `loop`, `label`, `tool`, and `tool_result` events append a live trace line.
8. `done` finalizes status, citations, model name, and elapsed time.
9. The assistant body is rendered by `MarkdownMessage` with `react-markdown` and `remark-gfm`.

The current renderer supports:

- headings
- paragraphs
- ordered and unordered lists
- blockquotes
- tables
- inline code and code blocks
- links

## Backend Flow

Main files:

- `backed/Services/Chat/ChatAppService.cs`
- `backed/Services/Chat/ChatWebSocketHandler.cs`
- `backed/Services/Chat/ChatOrchestrator.cs`
- `backed/Services/Chat/Agentic/AgentContext.cs`
- `backed/Services/Chat/Agentic/AgentLoop.cs`
- `backed/Services/Chat/Agentic/LabeledStep.cs`
- `backed/Services/Chat/Agentic/ToolProtocol.cs`
- `backed/Services/Chat/Agentic/ToolDispatch.cs`
- `backed/Services/Chat/Prompting/ChatPromptBuilder.cs`

Flow:

1. `ChatAppService` receives the streaming chat request and writes SSE frames.
2. `ChatOrchestrator` creates an `AgentContext`.
3. `AgentLoop` creates the first prompt and starts the label loop.
4. `LabeledStepRunner` streams one LLM call and parses the first label.
5. If the label is `TOOL`, `LabeledStepRunner` parses JSON tool calls.
6. `ToolDispatcher` executes each tool and returns observations plus citations.
7. `AgentLoop` appends tool observations and asks the model again.
8. When the model emits `FINISH`, the remaining text is the final Markdown answer.

WebSocket path:

1. `Program.cs` maps `/api/v1/chat/ws` after `UseWebSockets`.
2. `ChatWebSocketHandler` accepts one WebSocket client.
3. The browser sends one `ChatCompleteRequest` JSON message.
4. The handler calls `ChatOrchestrator.CompleteStreamingAsync`.
5. Each `AgentStreamEvent` is serialized as one WebSocket text message.
6. The socket closes normally after the `done` event, or sends an `error` event before closing on failure.

The WebSocket path and SSE path intentionally share the same event contract, so the UI can keep one event reducer and only swap the transport.

## Label Protocol

The model must start each LLM response with one of:

```text
FINISH
TOOL
THINK
```

`FINISH`:

The rest of the response is user-facing Markdown.

`TOOL`:

The rest of the response must be executable JSON:

```json
[
  {
    "name": "rag_search",
    "arguments": {
      "query": "question text",
      "top_k": 6
    }
  }
]
```

`THINK`:

The content is private reasoning and goes to the thinking stream, not the final answer.

## Current Tools

`rag_search`

Semantic retrieval over the selected knowledge base. Best for ordinary knowledge-base Q&A.

`read_page_range`

Reads chunks by PDF/document page range. Best for questions like "first 50 pages" or chapter/page summaries.

## DeepTutor Tool Design Notes

DeepTutor splits the agent into a few clear layers:

- `context.py`: carries the current run state, selected knowledge base, messages, usage, and trace data.
- `tool_protocol.py`: defines tool metadata, parameters, aliases, prompt hints, and normalized tool results.
- `tool_registry.py`: registers built-in tools and builds OpenAI function-calling schemas.
- `labeled_step.py`: runs one model call, parses labels, buffers final output, and separates thinking/tool/final channels.
- `tool_dispatch.py`: executes selected tools, aggregates observations, citations, and trace metadata.
- `loop.py`: repeats model calls until the agent has enough evidence and emits a final answer.

The important design choice is that tool calls are not normal answer text. Tool JSON, observations, and internal reasoning are trace events. Only `FINISH` content becomes the user-facing answer.

DeepTutor currently has built-in or capability-backed tools such as:

- `rag`: knowledge-base retrieval and citations.
- `web_search`: web lookup.
- `code_execution`: sandboxed code execution.
- `brainstorm` and `reason`: structured thinking helpers.
- `paper_search`: academic lookup.
- mastery and solve tools for tutor workflows.
- Obsidian tools for note search, read, backlinks, links, tags, create, append, and property updates.
- media generation and MCP adapter tools.

AiAgent now mirrors the same layering in C# with `AgentContext`, `ToolProtocol`, `ToolDispatcher`, `LabeledStepRunner`, and `AgentLoop`. The current implementation still uses a text `TOOL` JSON protocol for provider compatibility. The next stronger step is to let `LlmChatClient` send native OpenAI-compatible `tools` schemas and parse streamed `tool_calls`.

## Protocol Leak Fix

The label parser used to wait for only 32 characters before treating unknown output as `FINISH`. That allowed text such as apologies, `THINK`, and raw `TOOL` JSON to leak into the visible answer bubble.

The parser now:

- buffers up to 1024 characters while looking for the first label;
- recognizes labels that appear at the start of a later line;
- routes pre-label text to the `thinking` channel instead of `content`;
- treats unlabeled output as `THINK`, so the loop can repair and continue;
- allows the loop to continue with `TOOL` after a `THINK` round instead of forcing an early final answer.

## Why This Replaces The Rule Planner

The previous path used `KnowledgeQueryPlanner` to guess intent with keyword/regex rules. That is brittle:

- It can miss natural variants like "this book", "whole book", or "after page 50".
- It hardcodes one strategy for each phrasing.
- It cannot adapt when new tools are added.

The new primary path gives the model the tool protocol and lets the model decide which tool calls are needed. `KnowledgeQueryPlanner` remains in the codebase for compatibility, but `AgentLoop` no longer calls it on the main chat path.

## Remaining Improvements

- Add a `read_document_map` tool for document outline, title, page count, and chapter spans.
- Persist page summaries during indexing, then add a `read_page_summary` tool.
- Replace estimated token counts with real provider `usage` when the model API returns it.
- Move streaming from SSE to a resumable WebSocket if long-running turns need reconnect support.
- Add separate trace UI for tool calls instead of only updating the compact status row.
