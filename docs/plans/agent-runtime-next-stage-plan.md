# AiAgent 下一阶段规划与自有 Agent Loop 迭代路线

> 状态：规划稿  
> 日期：2026-09-08  
> 范围：`backed/Services/AgentRuntime`、`backed/Services/Chat` 及其前端诊断/交付投影  
> 前置基线：Native V2 已具备灰度入口、原生 tool calling、运行账本、调用 claim、上下文收缩、工具超时和单实例取消；默认路径仍为 legacy `AgentLoop`。

## 1. 结论

下一阶段的目标不是增加更多工具或过早引入多 Agent，而是让一个 Agent 任务可以被可靠地执行、暂停、恢复、审计和交付。

优先顺序如下：

1. 让运行状态和 continuation 成为可恢复的服务端事实源。
2. 完成审批、取消、重试和幂等工具调用的闭环。
3. 以只读工具和受限项目为范围完成 Native V2 影子验证与灰度切流。
4. 将任务、代码变更、验证结果和人工交付审批串成可追溯闭环。
5. 在上述能力稳定后，再评估计划器、子任务和多 Agent 编排。

```text
用户目标
  → Turn / Step 执行
  → 工具调用与运行账本
  → 审批、取消或可恢复 continuation
  → 验证证据（测试、diff、检查）
  → 变更集与人工交付审批
  → 可查询的最终结果
```

## 2. 当前基线与缺口

已具备：

- `RunCoordinator`、`AiAgentRun`、追加式 `AiAgentRunEvent` 和 owner/session 范围的运行查询。
- Native V2 的 OpenAI-compatible 原生工具调用、CallId/语义调用键防重、工具超时、上下文预算和工具计划快照。
- 只读工具的有限重试、工具输出截断、事件投影和 legacy 兼容入口。
- `WaitingApproval`、`WaitingInput` 状态枚举及恢复到 `Running` 的状态机路径。

仍不能对外承诺：

| 缺口 | 风险 | 下一步结果 |
| --- | --- | --- |
| 取消依赖执行进程内状态 | 重启、扩容或断连后无法可靠停止运行 | durable run lease 与跨实例取消信号 |
| 运行账本不包含 continuation | 不能在等待审批/输入或异常后安全续跑 | 加密/脱敏的可恢复执行检查点 |
| 工具 claim 仅阻止重放 | 崩溃后无法区分“已完成”和“执行中” | 调用状态、租约、结果摘要和恢复策略 |
| 审批尚未形成资源释放后的恢复闭环 | 审批状态可能悬挂或重复提交 | owner 校验、幂等审批决定、恢复队列 |
| 默认仍走 legacy loop | Native V2 尚未完成行为与安全基线验证 | 可量化影子比对与按模型/项目灰度 |
| 聊天结果与代码交付分离 | 用户无法判断任务是否真正完成 | 运行结果、验证证据、变更集、审批关联 |

## 3. 迭代原则

- **先事实源，后体验。** 前端状态、流事件和聊天文本都是投影；Run、Turn、Step、ToolCall 和审批决定才是恢复依据。
- **一次工具调用最多执行一次。** 每个调用都要有稳定 `CallId`、规范化参数哈希、状态和结果引用；不确定是否已执行的写工具不得自动重放。
- **暂停不占用执行槽。** `WaitingApproval` / `WaitingInput` 持久化后释放模型和工具资源；恢复时创建新的执行 lease。
- **失败应保守。** 网络重试仅适用于明确声明的只读、幂等工具；写工具需要 revision/幂等键或人工重新确认。
- **切流可回退。** 新旧循环并存期间，按模型、项目、用户或会话灰度；保留指标、审计和一键关闭开关。
- **交付必须有证据。** “模型回答完成”不等于“任务交付完成”；代码/配置变更必须附带验证结果和人工批准状态。

## 4. Phase D：可恢复执行与跨实例控制

### 交付内容

- 新增 `RuntimeContinuation` 持久化模型：保存 `RunId`、`TurnId`、当前 Step、历史 item 游标、工具计划快照哈希、预算、等待原因、版本号和过期时间。
- 新增 `RuntimeRunLease`：以数据库的原子条件更新或受控队列获取 run lease，包含 holder、租约到期、心跳和 fencing token。
- 将取消请求持久化为 `CancellationRequested`；执行节点轮询/订阅后终止模型和可取消工具。lease 失效后不得继续写入终态或执行写工具。
- 将工具调用状态收敛为 `Pending → Claimed → Running → Succeeded | Failed | TimedOut | Cancelled | Unknown`；保留脱敏结果摘要与幂等证据。
- 定义恢复策略：只读幂等调用可重试一次；写调用若处于 `Unknown`，转为 `WaitingApproval` 或要求用户重新发起，绝不自动重放。

### 验收

- 服务重启后，运行不会同时在两个实例执行；过期 lease 无法继续提交事件。
- 用户从任意实例发出的停止请求会在目标实例可见，并最终写入一致终态。
- 在模型调用、只读工具、写工具三个中断点注入故障，账本与后续行为符合恢复策略。
- 重放事件后，步骤序列、工具状态和最终结果没有重复的副作用记录。

## 5. Phase E：审批和用户追加输入闭环

### 交付内容

- `ApprovalRequest` 作为独立持久化资源，含审批类别、风险摘要、参数摘要、目标资源、过期时间、owner 和一次性决定 ID。
- 审批 API 仅接受 allow/deny 与受控备注；校验 owner、run、request 和当前状态，重复提交返回同一决定。
- `WaitingInput` 使用受控输入队列，记录输入类型和上限；恢复时将输入作为新的 runtime item，不拼接到旧 prompt 字符串。
- 审批、输入、取消和 timeout 统一由状态机处理，所有转移先持久化再广播事件。

### 验收

- 审批等待期间不占用模型/工具并发槽。
- 非 owner、过期、已终态或重复的审批请求均不能产生第二次工具执行。
- 用户补充输入后从正确 Step 继续，历史中不存在孤立 tool-call/tool-result 配对。

## 6. Phase F：Native V2 影子验证与灰度切流

### 交付内容

- 建立回放测试集：知识检索、代码检索、看板只读、看板写入拒绝/审批、超时、取消、异常工具输出、长上下文和多工具调用。
- 在不执行副作用的场景下提供 shadow compare：同一受控输入比较 legacy 与 Native V2 的工具选择、终止、引用、用量和错误分类；不记录 prompt/原始工具正文。
- 增加按模型、项目和用户分层的开关与熔断阈值；Native V2 首先仅开放只读工具与内部测试项目。
- 监控指标：完成率、协议失败率、工具重复率、P50/P95 时长、取消收敛时间、恢复成功率、每 Turn token/成本、人工介入率。

### 切流门槛

| 阶段 | 可用范围 | 必须满足 |
| --- | --- | --- |
| 影子 | 内部测试、无副作用 | 回放通过；无重复调用；事件/账本一致 |
| 小流量 | 指定模型、只读工具 | 协议失败和超时不劣于 legacy；支持回退 |
| 受控写入 | revision 保护的写工具 | 审批、Unknown 处理、故障演练通过 |
| 默认启用 | 全量原生支持模型 | 连续稳定观察期通过，legacy 保留降级开关 |

任何阶段发现安全边界、重复写入或账本不一致时，立即关闭相应 Native 开关，保留账本用于诊断；不以静默回退掩盖问题。

## 7. Phase G：研发交付闭环

Agent loop 的完成语义应拆分为“回答完成”“运行完成”“交付已验证”“人工已批准”，避免将文本回答误判为变更已交付。

### 交付内容

- 为运行结果关联受控工作项、代码仓库/看板 workspace revision、变更文件清单、测试/校验摘要和失败原因。
- 新增不可变 `DeliveryChangeSet` 概念：包含产生它的 Run/Turn、目标范围、diff 摘要、验证证据、审批快照指纹和交付状态。
- Agent 只能创建变更集和建议交付，不能绕过人工批准推送远端；复核审批指纹后由具备权限的人工执行提交/发布。
- 聊天与工作台展示清晰状态：`draft`、`verified`、`approval_required`、`approved`、`delivered`、`rejected`。

### 验收

- 每一项写入型任务都能定位到执行 Run、工具调用、文件/revision、验证和审批结果。
- 验证失败或执行取消不会生成可交付状态。
- 审批后的内容发生变化时，审批快照失效，必须重新验证和审批。

## 8. 多 Agent 的进入条件与最小形态

多 Agent 不应作为下一阶段主线。只有满足以下前提后才启动试点：可恢复运行稳定、写工具审批闭环、交付变更集可追踪，并且单 Agent 的失败分类已有足够数据。

首个试点建议使用“主 Agent + 受限专家子任务”，而不是开放式互相对话：

- 主 Agent 负责目标分解、上下文选择、最终合并和交付建议。
- 子任务只允许只读检索、代码分析、测试计划或受控验证；输出为结构化事实、引用和置信度，不直接写工作区。
- 每个子任务拥有独立预算、超时、工具计划和 event stream；主 Agent 只能引用已完成、可审计的结果。
- 共享状态通过版本化 artifact/引用传递，禁止共享可变 `AgentContext` 或隐式 prompt 拼接。

试点验收指标是“减少人工重复检索/验证时间且不增加错误写入”，而不是并发 Agent 数量。

## 9. 建议排期与优先级

以一个小型跨职能小组为例，建议按以下顺序推进；每一阶段结束后根据指标决定是否进入下一阶段。

| 周期 | 重点 | 关键产物 |
| --- | --- | --- |
| 第 1–2 周 | Phase D | continuation、lease、跨实例取消、故障恢复测试 |
| 第 3 周 | Phase E | 审批/补充输入资源与恢复 API、前端状态投影 |
| 第 4–5 周 | Phase F | 回放集、影子比对、只读工具灰度、指标看板 |
| 第 6–7 周 | Phase G | 变更集、验证证据、人工审批与交付视图 |
| 第 8 周后 | 多 Agent 试点 | 仅限只读专家子任务，按指标扩展 |

若资源有限，优先完成 Phase D 的 run lease、取消和写工具 `Unknown` 状态处理；这三项直接决定长任务是否可信。

## 10. 测试与运维清单

- 单元测试：状态机、lease fencing、工具幂等键、审批幂等、上下文 item 配对、预算和终止策略。
- 集成测试：双实例竞争、重启恢复、数据库短暂不可用、模型超时、工具超时、取消与审批并发。
- 契约测试：OpenAI-compatible tool-call 流、legacy event projector、前端 run/event DTO。
- 安全测试：越权取消/审批、伪造 CallId、工具快照漂移、路径/附件泄漏、重复写入和过期 approval。
- 运行手册：灰度开关、熔断条件、账本检索、卡住 run 的处置、数据保留和事件脱敏复核。

## 11. 明确暂不做的事项

- 不在 durable continuation 之前宣称支持跨实例恢复。
- 不让模型直接执行 shell、传递文件系统绝对路径、指定任意 sandbox 或拼接外部进程参数。
- 不让写工具因网络异常自动重试。
- 不将推理链、原始 prompt、附件正文、令牌或真实路径写入运行账本。
- 不在单 Agent 可靠性尚未验证前扩大为自治多 Agent 编排。
