# AiAgent 浏览器工作区方案（Codex CLI 接入）

日期：2026-10-08  
状态：方案草案，尚未实现。

## 1. 目标与体验

保留 AiAgent 当前的 Codex CLI 接入，在聊天界面右侧增加浏览器工作区。用户通过左侧聊天下达目标，Codex 调用浏览器工具执行，右侧展示同一个浏览器的实际画面；用户可以随时接管，再交还给 AI。

```text
┌───────────────────────────────────────────────────────────┐
│ AiAgent · 当前项目                         浏览器工作区    │
├───────────────────────┬───────────────────────────────────┤
│ 聊天                  │ 地址 / 状态                        │
│                       │ [暂停] [我来操作] [交给 AI] [结束] │
│ 帮我测试登录和新增功能 │                                   │
│                       │ 真实浏览器画面                    │
│ AI：正在打开测试地址  │ 能看见页面、点击、输入和跳转       │
│                       │                                   │
│ 进度、问题、结果      │ 下载文件 / 截图 / 操作记录         │
└───────────────────────┴───────────────────────────────────┘
```

AiAgent 是任务入口；被操作的网站运行在后台管理的浏览器中。右侧接收画面并转发鼠标键盘输入，不要求目标网站改造，也不直接用 iframe 嵌入目标网站。

网页测试只是用途之一，同样可以用于后台查询、资料录入、报表下载和跨系统操作。复杂任务仍需基于实际执行证据判断结果，不能把点击成功等同于业务成功。

## 2. 已确认的接入基础

当前代码 `backed/Services/Chat/Codex/CodexChatService.cs` 通过 `ProcessStartInfo.ArgumentList` 添加 `app-server`、`--stdio` 启动 Codex，并处理其协议消息。

本方案在这条聊天链路上增加浏览器工具入口。浏览器执行、画面传输、会话管理和人工接管属于新增能力，不应把现有 Codex 进程池中的“browser runtime”命名理解为已经具备远程浏览器功能。

## 3. 总体架构

```text
AiAgent 前端
  ├─ 左侧聊天 ────────── AiAgent 后端 ───── Codex app-server
  └─ 右侧浏览器工作区         │                      │
       │                     │ 会话管理             │ 工具调用
       │                     ▼                      ▼
       │               Browser Session Service / 工具桥接
       │                     │
       │                     ▼
       └─ 画面与人工输入 ─ Browser Worker
                             ├─ 浏览器自动化
                             ├─ 画面采集与输入转发
                             └─ 同一个 Chromium 会话
```

建议以 Playwright 控制 Chromium，后端统一分配和管理浏览器会话。工具调用和右侧画面必须绑定同一个 `browserSessionId`，不能分别启动两套浏览器。

Codex 工具入口优先评估 MCP 适配；具体注册方式、当前 CLI 版本支持情况及会话隔离机制，在实施前通过本地版本和最小验证确定。本文不把尚未验证的协议能力列为已完成能力。

## 4. 各部分职责

| 部分 | 职责 |
| --- | --- |
| Codex CLI | 理解目标、观察页面、决定下一步、组织结果 |
| AiAgent 后端 | 校验权限、绑定聊天与浏览器会话、管理控制权及生命周期 |
| 浏览器工具桥接 | 提供导航、页面观察、点击、输入、滚动、截图等受控操作 |
| Browser Worker | 执行自动化、采集画面、接收人工输入、管理下载产物 |
| 前端浏览器工作区 | 展示画面、操作状态、人工接管入口和执行结果 |

建议新增 `backed/Services/Browser/` 领域服务及配套 DTO；前端新增浏览器工作区组件，接口和类型分别放入 `front/lib/`。这些路径为拟议模块，并非现有实现。

## 5. 实时画面如何实现

第一阶段建议验证 Chromium 画面采集加 WebSocket 转发：前端使用 Canvas 展示帧，人工接管时将点击、滚动、按键和文本输入传回 Worker。需要处理画面缩放、坐标映射、中文输入、焦点、帧丢弃及断线恢复。

这一路线适用于网页视口操作。浏览器原生弹窗、文件选择器和完整桌面交互不能仅靠页面画面覆盖；文件上传下载应提供专门入口。

如果验证后需要完整浏览器窗口或桌面接管，可采用隔离图形环境加 noVNC；对画面延迟和流畅度要求更高时，再评估 WebRTC。具体方案由部署环境和最小验证结果决定，不预设 Windows 后台服务必然具备交互式桌面。

## 6. 人工接管与执行流程

1. 用户打开工作区，后端创建浏览器会话并绑定当前用户、项目和聊天。
2. 用户提供网站地址与任务；Codex 通过工具桥接观察并操作页面。
3. Worker 将执行状态和实时画面返回前端。
4. 遇到登录、验证码或需要用户判断的页面，进入等待人工状态。
5. 用户点击“我来操作”：后端停止接收新的 AI 操作，等待正在执行的动作结束或确认取消后，再授予人工控制权。
6. 用户操作完成后点击“交给 AI”：后端收回人工写入权限，Codex 重新观察当前页面再继续。
7. 完成后返回结果、截图和下载文件；结束会话时释放浏览器资源。

建议状态包括：创建中、AI 操作中、暂停、等待人工、人工操作中、失败、已关闭。控制权以服务端为准，使用控制版本或租约拒绝过期输入，避免 AI 和用户同时操作。

## 7. 被测试的网站在哪里运行

测试开发中的网页时，需要先启动对应项目；涉及接口和数据库的功能，还需要相关后端服务就绪。后续可接入项目现有运行管理能力，将“启动测试环境 → 检查就绪 → 打开网页 → 执行测试”串联起来。

测试已部署网站时直接使用其地址。

`localhost` 指浏览器 Worker 所在环境。如果 Worker 在服务器或容器中，它不能通过自己的 `localhost` 访问用户电脑上的服务；必须使用从 Worker 可访问的地址。项目运行服务和浏览器会话分别管理，关闭浏览器不应误停其他任务的服务。

## 8. 会话、权限与产物

- 创建、查看画面、输入、接管、下载及结束操作都校验用户和项目权限。
- 浏览器登录态按用户及会话隔离，不直接复用服务器日常浏览器配置。默认会话结束即清理，持久化登录态作为后续单独配置能力。
- 工具桥接通过服务端绑定获取目标会话，不允许模型仅凭任意会话 ID 操作其他用户的浏览器。
- 页面内容视为外部数据，不能借网页中的指令扩大任务权限。网站访问范围沿用用户授权，并在部署时配置必要的网络边界。
- 截图、操作记录和下载文件存放于受控目录；通过授权下载接口交付，不暴露宿主机路径，不记录密码、Cookie 或令牌。
- 断线时暂停自动操作并保留有限恢复窗口；超时、取消、后端重启和 Worker 崩溃均需显式处理，不自动重放可能产生业务副作用的操作。

## 9. 分阶段实施

### 第一阶段：验证同一浏览器的端到端链路

完成单用户单会话验证：打开测试页、工具点击输入、右侧实时画面、人工接管、交还 AI、关闭资源。先证明三方共享同一个浏览器状态，再接入完整业务流程。

### 第二阶段：融入聊天工作台

加入右侧面板、会话绑定、状态展示、Codex 工具适配、任务进度、截图及下载入口；复用项目权限和运行管理能力。

### 第三阶段：完善稳定性与多用户能力

补齐并发配额、会话隔离、断线恢复、空闲回收、多标签页、下载清理和部署监控。根据实际延迟与接管需求决定是否升级画面传输方案。

## 10. 验收标准

- 左侧下达任务后，右侧可看到对应浏览器的真实变化。
- AI 点击和人工操作影响同一个页面与登录状态。
- 人工接管生效后不再执行新的 AI 写操作，过期控制指令被拒绝。
- 交还 AI 后重新读取页面状态，不继续依赖接管前的旧元素引用。
- 能完成测试页面上的导航、输入、提交和结果校验，并提供执行证据。
- 无权用户不能查看画面、控制会话或下载产物。
- 断线、取消和会话结束有明确状态，浏览器进程及临时资源按策略释放。

本文保存的是拟议实现方案，不代表浏览器工作区已开发或部署。
